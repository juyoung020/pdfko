# pdfko

영문 교재 PDF를 **레이아웃 그대로** 한국어로 번역한다. 수식·그림·표는 원본 벡터를 그대로 다시 그리므로 훼손되지 않고, 쪽번호도 원본과 일치한다. 전부 로컬 GPU에서 돌아가고 유료 API를 쓰지 않는다.

```bash
pdfko-web            # 브라우저에서 끌어다 놓고 버튼 하나
pdfko book.pdf       # 또는 명령줄
```

## 무엇이 다른가

교재를 번역하는 도구는 이미 있다. 이 프로젝트는 그 위에 **한국어와 수학 교재에 특유한 문제들**을 얹어 해결한다. 500쪽짜리 교재 한 권을 실제로 번역하면서 하나씩 부딪힌 것들이고, 각 항목은 그때 측정한 숫자를 달고 있다.

### 수식은 번역하지 않는다

수식을 폰트 이름으로 식별해 통째로 마스킹하고, 번역이 끝나면 **원본 벡터 글리프를 그 자리에 다시 그린다.** 모델이 수식을 볼 일이 없으니 훼손될 수 없다. 그림과 표도 같다.

자리표시자가 15개 넘게 박힌 문단(기호 정리표 같은 것)은 모델이 전부 정확히 복사하지 못하고 몇 개를 흘린다. 그런 문단은 자리표시자와 태그 **사이의 본문만** 번역하고 나머지는 원위치에 되돌린다.

```
원문:  where {v1}is <style id='2'>soft-max</style> and {v3} holds
조각:  ['where ', 'is ', 'soft-max', ' and ', ' holds']   ← 모델에 이것만
보존:  ['{v1}', "<style id='2'>", '</style>', '{v3}']     ← 도구가 되돌림
```

조각을 되돌려 붙인 결과도 검사한다. 조각 하나하나는 `column ` 처럼 짧아서 "영어가 그대로 돌아왔다"는 판정을 빠져나가므로, **다시 짜맞춘 문단 전체**를 원문과 견준다. 이걸 빠뜨렸을 때 영어 원문이 성공으로 집계되고 그대로 캐시에 박혀, 정상 모델로 다시 물어도 영어가 나왔다.

### 원본에 숨어 있는 글자를 먼저 치운다

교재의 그림 중에는 다른 문서 페이지를 통째로 가져와 **잘라내기로 필요한 부분만 남긴** 것이 있다. 잘라내기는 화면에서 가릴 뿐 파일에서 글자를 지우지 않는다.

번역 엔진은 그 가림을 무시한다. 숨은 글자까지 전부 번역해서 **진짜 본문 위에 겹쳐 찍는다.** 한 교재에서 실측하니 페이지 한 장에 숨은 글자가 1,094자, 책 전체 글자의 3.8%였고, 겹쳐 찍히는 페이지가 14장 나왔다.

그래서 번역 전에 원본 사본을 만들어 잘라내기 영역 밖 글자를 제거한다. 페이지마다 지운 뒤 **보이는 텍스트를 원본과 글자 단위로 대조**하고, 손실이 한도를 넘으면 그 페이지는 원상 복구한다. 임계값을 손으로 맞추는 대신 보장을 만든다.

세는 단위가 중요하다. PDF의 텍스트 연산자 하나(`Tj`)에는 글자가 몇 개든 들어간다. 연산자를 세면 5,000자가 숨은 페이지도 `1`로 잡혀 임계값을 못 넘는다. 피연산자를 해석해 **글자 수**를 센다 — `(text)`, `<hex>`, 커닝이 섞인 `[(a) -20 (b)] TJ` 모두.

같은 이유로 안전장치도 세 형태를 다 읽어야 한다. 괄호 문자열만 보던 시절에는 pdfTeX가 내놓는 커닝 배열과 서브셋 폰트의 16진 문자열이 전부 빠져나가, "보이는 낱말은 지킨다"는 장치가 **실제 본문 대부분에서 동작하지 않았다.**

손실 한도도 개수만으로는 부족하다. 보이는 낱말이 원래 하나인 페이지에서 그 하나를 잃으면 손실률 100%인데 `1 ≤ 3`이라 통과한다. 비율(20%) 상한을 함께 건다.

| 원본쪽 | 청소 전 | 청소 후 |
|---|---|---|
| 299 | 겹침 57% | 정상 |
| 445 | 겹침 32% | 정상 |
| 155 | 겹침 19% | 정상 |

이 원인을 찾기 전에는 "한국어가 영어보다 길어 자리가 부족하다"고 생각했다. 실측하니 **한국어가 오히려 짧았다** — 정상 페이지 470장의 폭 비율 중앙값 0.93배, 1.2배를 넘는 페이지는 하나도 없었다.

### 깨진 텍스트 레이어를 복구한다

LaTeX으로 만든 PDF를 다른 도구가 다시 저장하면 폰트의 ToUnicode 정보가 사라져 추출 텍스트가 망가진다. 까다로운 점은 **같은 문자가 원본 폰트에 따라 다른 글자를 뜻한다**는 것이다.

| 추출된 문자 | 본문 폰트에서 | 수학 폰트에서 |
|---|---|---|
| `↵` | **ff** 합자 | α |
| `⇡` | — | π |
| `✓` | — | θ |

`di↵erent`는 `different`가 맞지만 `↵w`는 `αw`이지 `ffw`가 아니다. 앞 글자가 라틴 문자인지로 판별한다. `pdffonts`에 `uni no`가 보이면 이 손상을 의심하면 되고, 도구가 시작할 때 자동으로 알려준다.

더 성가신 쪽은 **번역 엔진이 이 합자를 수식으로 오인하는 것**이다. `di↵erent`가 `di{v1}erent`로 마스킹되고, 번역이 끝나면 그 자리에 원래 글리프(`↵`)를 도로 그린다. 한국어 문장 한가운데 `↵`가 박히는 이유다.

그래서 번역 전에 원본을 훑어 **어느 조합이 진짜 합자였는지** 사전을 만들고, 그 자리표시자만 골라 녹인다. 사전에 없는 조합은 진짜 수식이므로 손대지 않는다.

```
di{v1}erent                                   → different     (사전에 있음)
<style id='4'>temporal-di</style>{v6}erence   → difference    (태그 건너뜀)
where {v1}is a small positive fraction        → 그대로        (진짜 α)
```

자리표시자만 글자로 바꾸고 **태그는 건드리지 않는다.** 태그까지 함께 지우면 `<style>`이 짝을 잃는 배치가 있다. 무작위 조합 4,096건으로 오탐을 쟀고 0건이었다.

### 레이아웃 파손을 감지하고 되살린다

한국어를 넣으면 글자가 겹치거나 여백 밖으로 밀려나는 페이지가 생긴다. **그런데 텍스트 추출로는 이게 보이지 않는다.** 한글 비율도 정상이고 미번역도 아니다. 지표만 보면 멀쩡한데 실물은 못 읽는다.

렌더링된 페이지에서 **단어의 실제 좌표를 원본과 대조**해 세 가지를 잰다 — 겹침, 영역이탈, 줄충돌. 여기에 그림 속 라벨 일부만 번역되어 언어가 섞이는 경우를 따로 센다.

절대 기준으로 재면 안 된다. 수식이 빽빽한 페이지는 **원본에서도** 상자가 겹치게 조판되어 있다(위·아래 첨자, 큰 괄호). 같은 지표를 원본에서도 재고 **늘어난 만큼만** 본다.

렌더링된 픽셀의 잉크 농도로도 재봤지만 원리적으로 부족했다. 한국어로 바뀌면 글자 수가 줄어 잉크가 옅어지는 게 정상이라(중앙값 0.84배), 파손됐는데도 옅은 페이지를 구분할 수 없다.

```
                     텍스트 지표   잉크 농도    단어 좌표
겹쳐서 못 읽는 쪽        통과      3.38 ✓      겹침 57% ✓
여백으로 밀려난 쪽        통과      1.41 ✗      이탈 19% ✓
글자가 뒤섞인 쪽         통과      0.64 ✗      이탈 14% ✓
그림 라벨만 섞인 쪽       통과      0.69 ✗      그림혼재 ✓
```

감지했으면 **되살려야 한다.** 원문으로 돌려놓는 것은 고치는 게 아니라 포기하는 것이다. 그래서 사다리를 둔다.

```
1단계  그 페이지만 '간결하게' 다시 번역한다   ← 겹침의 원인은 길이다
2단계  그래도 안 되면 원문 페이지를 그대로 쓴다
```

1단계는 그 한 쪽만 다시 돌리므로 40쪽 구간을 재번역할 필요가 없다. 실측으로 겹침 99%로 표시한 페이지가 간결 재번역만으로 한국어(1,046자)를 유지한 채 정상 판정을 받았다.

2단계까지 간 페이지는 영어로 남는다. 그때는 **조용히 바꿔치기하지 않는다.** 해당 쪽 하단에 표시를 남기고 보고서에 기록한다. 그러지 않으면 사용자는 "번역이 빠졌다"고만 느낀다.

### 실패한 항목만 다시 보낸다

배치 10개 중 1개가 틀렸다고 10개를 재번역하면 GPU가 재작업만 한다. 항목별로 검증해 실패한 것만 골라 다시 보내고, 그때 **"당신은 `{v38}`을 빠뜨렸다"**고 이름으로 지목한다.

### 캐시는 문단 단위다

번역 엔진은 실행마다 문단을 다르게 묶고 번호를 다시 매긴다. 배치 전체를 한 키로 해시하면 묶음이 조금만 달라져도 전부 빗나간다 — 500쪽 작업에서 실측 적중률 **2.18%**였다. 같은 문장이 실행마다 다르게 번역되어 용어까지 흔들렸다.

문단 하나를 캐시 한 줄로 바꾸고 id를 키에서 뺐다.

| 시나리오 | 이전 | 지금 |
|---|---|---|
| 같은 배치 재요청 | 적중 | 2/2 |
| 배치에 1개 추가 | 전부 미스 | 2/3 |
| 같은 문장, id만 다름 | 미스 | 2/2 |
| 부분집합 | 미스 | 1/1 |

검증 규칙을 바꾸면 캐시가 자동으로 무효화되도록 **모듈 소스 전체를 해시해 키에 넣는다.** 예전에는 함수 세 개만 해시해서, 여덟 군데를 고쳐도 지문이 그대로였다. 같은 수정을 네 번 반복하게 만든 원인이었다.

**사용자가 바꾼 것도 키에 들어간다.** 용어집과 추가 프롬프트는 시스템 메시지로 실려 오는데, 한동안 이게 키에서 빠져 있었다. 개발자가 고친 규칙은 지문에 넣으면서 정작 사용자가 바꾼 입력은 무시한 셈이라, 용어집을 바꿔도 옛 번역이 그대로 나왔다.

3쪽 문서로 실측한 왕복 시간은 냉캐시 59초, 온캐시 19초로 **3.1배**다. 고정 비용(엔진 기동·조판 해석·파손 검사)이 큰 짧은 문서라 이 정도고, 쪽수가 늘수록 비율은 더 벌어진다.

### 같은 프로세스를 두 번 믿지 않는다

`uvicorn`은 `--reload` 없이 뜨면 **기동 시점의 코드를 계속 쓴다.** 그런데 예전 구현은 `/health`가 응답하기만 하면 그 프록시를 재사용했다. 그래서 소스를 고쳐도 몇 시간 묵은 프로세스가 계속 서비스했고, 검증은 전부 옛 코드를 상대로 이루어졌다.

이 프로젝트에서 가장 많은 시간을 잡아먹은 실패다. 13시간 된 프로세스를 상대로 "고쳤다"를 반복했다.

지금은 `/health`가 규칙 지문을 내보내고, 지문이 다르면 **살아 있어도 죽은 것으로 본다.**

다만 **갈아치우지는 않는다.** 처음 구현은 포트를 쥔 프로세스를 그냥 죽였다. 우리 것인지 보지도 않고. 8100은 흔한 개발 포트라, 이 도구를 처음 받아 실행한 사람이 무관한 서버를 잃는다. 두 번역을 동시에 돌리면 나중 것이 먼저 것의 프록시를 죽였고, 먼저 것은 합자 사전 없는 프록시로 넘어가 한국어 본문에 `↵`가 15개 박힌 채 **"파손 0쪽"이라고 보고했다.**

지금은 `/health`의 모양으로 우리 것인지 확인하고, 남의 것이면 죽이지 않고 **다음 빈 포트로 비켜 간다.** 같은 작업 디렉터리의 프록시만 이어 쓴다.

## 설치

```bash
uv tool install --python 3.12 babeldoc      # 번역 엔진
sudo apt install poppler-utils              # pdffonts (선택)
pip install -e .
```

추론은 [ollama](https://ollama.com)를 쓴다. 번역 특화 모델을 권한다.

```bash
hf download tencent/Hy-MT2-7B-GGUF --include "*Q6_K*" --local-dir ~/models
pdfko book.pdf --gguf ~/models/HY-MT2-7B-Q6_K.gguf     # 최초 1회만
```

## 사용

```bash
pdfko-web                             # 브라우저 화면 (http://127.0.0.1:8000)

pdfko book.pdf                        # 전체
pdfko book.pdf -p 13-502              # 본문만 (참고문헌·색인 제외)
pdfko book.pdf --glossary rl.csv      # 용어집 적용
pdfko book.pdf --recheck              # 번역 건너뛰고 검사·복구만
pdfko book.pdf --fresh                # 캐시 비우고 처음부터
pdfko deck.pptx                       # 발표자료 (서식 유지)
```

용어집은 `source,target` 헤더를 가진 CSV다. `glossaries/rl.csv`에 강화학습 용어 108개가 들어 있다.

중간에 끊겨도 같은 명령을 다시 실행하면 이어서 간다. 구간 단위 표식과 문단 단위 캐시가 이중으로 받쳐 준다.

## 하드웨어

12GB VRAM(RTX 3060)에서 7B 모델로 검증했다. 500쪽 교재에 3~5시간.

**GPU 사용률이 낮으면 레이어 오프로드를 의심할 것.** ollama 로그의 `offloaded N/M layers`에서 N과 M이 다르면 일부가 CPU에서 돌고 있다는 뜻이고, 토큰마다 CPU를 왕복하느라 GPU가 20%대에 머문다. 슬롯 수를 늘리면 KV 캐시가 커져 오히려 레이어를 GPU 밖으로 밀어낸다. 이 도구는 8슬롯으로 고정해 12GB에서 전 레이어가 GPU에 남도록 했다.

## 알려진 한계

**그림 속 라벨이 일부만 번역될 수 있다.** 짧은 라벨이 길이 기준에 걸려 제외되면 다이어그램 안에서 언어가 섞인다. 검사에서 잡아 보고서에 남기지만 자동으로 고치지는 않는다.

**PPTX는 문장 속 부분 강조를 잃는다.** 한 문단이 여러 런으로 쪼개져 있으면 번역문을 가장 긴 런에 넣고 나머지를 비운다. 문장 단위 어순을 지키려면 합쳐야 하고, 합치면 부분 강조가 사라진다. 하이퍼링크도 같은 이유로 끊긴다.

**차트와 SmartArt 안의 글자는 번역되지 않는다.** 슬라이드가 아니라 별도 XML 파트(`<c:v>` 문자열 캐시)에 살아서 도형 순회로는 닿지 않는다. 다만 **세어서 알려준다** — 영어가 남아 있는데 "100% 번역"이라고 말하지는 않는다.

```
▶ 완료
  결과 deck_한국어.pptx
  ! 차트·SmartArt 안의 텍스트 4개는 번역되지 않았습니다 (파워포인트 한계)
      Accuracy
      Training
```

**각주가 번역되지 않는 경우가 있다.** 번역 엔진이 특정 크기의 이탤릭 폰트를 수식으로 오분류한다. 판별 규칙을 바꾸면 진짜 수식이 번역 대상이 될 위험이 있어 기본값을 유지한다.

**엔진이 수식을 원위치에 복원하지 못하는 페이지가 드물게 있다.** 텍스트가 뒤섞인 페이지에서 `{v1}`이 글자로 남는다. 재번역해도 같은 자리에서 실패한다. 미들웨어 바깥의 문제라 손댈 수 없다.

## 개발

```bash
env -u PYTHONPATH .venv/bin/python -m pytest tests/ -q
```
