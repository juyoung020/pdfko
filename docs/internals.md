# 내부 동작

500쪽짜리 교재 한 권을 실제로 번역하면서 부딪힌 문제들과 그 해결 방법입니다. 각 항목은 그때 측정한 숫자를 달고 있습니다.

## 구조

```
book.pdf
   │
   ▼
BabelDOC ─── 레이아웃 분석, 수식을 폰트 이름으로 식별해 마스킹
   │
   │  OpenAI 호환 HTTP
   ▼
미들웨어 프록시 (pdfko)
   │   합자 복구 · 용어집 · 자리표시자 검증 · 재시도 · 캐시
   │
   ▼
ollama ─── Hy-MT2-7B
```

BabelDOC은 원문 텍스트에 손댈 훅을 주지 않습니다. 그래서 요청이 모델에 닿기 전에 가로채는 프록시를 끼웠습니다.

## 수식은 번역하지 않는다

수식을 폰트 이름으로 식별해 통째로 마스킹하고, 번역이 끝나면 **원본 벡터 글리프를 그 자리에 다시 그립니다.** 모델이 수식을 볼 일이 없으니 훼손될 수 없습니다. 그림과 표도 같습니다.

자리표시자가 15개 넘게 박힌 문단(기호 정리표 같은 것)은 모델이 전부 정확히 복사하지 못하고 몇 개를 흘립니다. 그런 문단은 자리표시자와 태그 **사이의 본문만** 번역하고 나머지는 원위치에 되돌립니다.

```
원문:  where {v1}is <style id='2'>soft-max</style> and {v3} holds
조각:  ['where ', 'is ', 'soft-max', ' and ', ' holds']   ← 모델에 이것만
보존:  ['{v1}', "<style id='2'>", '</style>', '{v3}']     ← 도구가 되돌림
```

조각을 되돌려 붙인 결과도 검사합니다. 조각 하나하나는 `column ` 처럼 짧아서 "영어가 그대로 돌아왔다"는 판정을 빠져나가므로, **다시 짜맞춘 문단 전체**를 원문과 견줍니다. 이걸 빠뜨렸을 때 영어 원문이 성공으로 집계되고 그대로 캐시에 박혀, 정상 모델로 다시 물어도 영어가 나왔습니다.

## 원본에 숨어 있는 글자를 먼저 치운다

교재의 그림 중에는 다른 문서 페이지를 통째로 가져와 **잘라내기(clipping)로 필요한 부분만 남긴** 것이 있습니다. 잘라내기는 화면에서 가릴 뿐 파일에서 글자를 지우지 않습니다.

번역 엔진은 그 가림을 무시합니다. 숨은 글자까지 전부 번역해서 **진짜 본문 위에 겹쳐 찍습니다.** 한 교재에서 실측하니 페이지 한 장에 숨은 글자가 13,016자, 책 전체 글자의 3.8%였고, 겹쳐 찍히는 페이지가 14장 나왔습니다.

| 원본쪽 | 청소 전 | 청소 후 |
|---|---|---|
| 299 | 겹침 57% | 정상 |
| 445 | 겹침 32% | 정상 |
| 155 | 겹침 19% | 정상 |

이 원인을 찾기 전에는 "한국어가 영어보다 길어 자리가 부족하다"고 생각했습니다. 실측하니 **한국어가 오히려 짧았습니다** — 정상 페이지 470장의 폭 비율 중앙값 0.93배, 1.2배를 넘는 페이지는 하나도 없었습니다.

### 세는 단위

PDF의 텍스트 연산자 하나(`Tj`)에는 글자가 몇 개든 들어갑니다. 연산자를 세면 5,000자가 숨은 페이지도 `1`로 잡혀 임계값을 못 넘습니다. 피연산자를 해석해 **글자 수**를 셉니다 — `(text)`, `<hex>`, 커닝이 섞인 `[(a) -20 (b)] TJ` 모두.

### 보이는 글자는 잃지 않는다

두 겹으로 막습니다.

1. **MuPDF가 보인다고 한 자리는 지우지 않습니다.** 글자를 대조하려 했지만 원리적으로 안 됩니다 — CID 폰트(Identity-H)는 2바이트 글리프 번호를 싣고, 그게 무슨 글자인지는 폰트의 CMap을 읽어야 압니다. 서브셋으로 심어 온 페이지가 바로 이 모듈이 다루려는 대상인데, 거기서 안전장치가 통째로 무력해졌습니다. 그래서 **좌표로** 봅니다. 폰트와 무관하고 `Tj`·`TJ`·`<hex>`를 가리지 않습니다.

2. **지운 뒤 대조하고 되돌립니다.** 보이는 텍스트가 달라지면 그 페이지는 원상 복구합니다. 손실 한도는 개수(3개)와 비율(20%)을 함께 겁니다. 개수만으로는 부족합니다 — 보이는 낱말이 원래 하나인 페이지에서 그 하나를 잃으면 손실률 100%인데 `1 ≤ 3`이라 통과합니다.

손실 계산은 집합이 아니라 **중복집합**으로 합니다. 머리글이 반복되거나 두 단 레이아웃에서 같은 낱말이 양쪽에 있으면, 한쪽을 통째로 지워도 "모든 낱말이 어딘가엔 남아 있으니 손실 0"이 되어 조용히 통과합니다.

## 깨진 텍스트 레이어를 복구한다

LaTeX으로 만든 PDF를 다른 도구가 다시 저장하면 폰트의 ToUnicode 정보가 사라져 추출 텍스트가 망가집니다. 까다로운 점은 **같은 문자가 원본 폰트에 따라 다른 글자를 뜻한다**는 것입니다.

| 추출된 문자 | 본문 폰트에서 | 수학 폰트에서 |
|---|---|---|
| `↵` | **ff** 합자 | α |
| `⇡` | — | π |
| `✓` | — | θ |

`di↵erent`는 `different`가 맞지만 `↵w`는 `αw`이지 `ffw`가 아닙니다. 앞 글자가 라틴 문자인지로 판별합니다. `pdffonts`에 `uni no`가 보이면 이 손상을 의심하면 되고, 도구가 시작할 때 자동으로 알려줍니다.

더 성가신 쪽은 **번역 엔진이 이 합자를 수식으로 오인하는 것**입니다. `di↵erent`가 `di{v1}erent`로 마스킹되고, 번역이 끝나면 그 자리에 원래 글리프(`↵`)를 도로 그립니다. 한국어 문장 한가운데 `↵`가 박히는 이유입니다.

그래서 번역 전에 원본을 훑어 **어느 조합이 진짜 합자였는지** 사전을 만들고, 그 자리표시자만 골라 녹입니다. 사전에 없는 조합은 진짜 수식이므로 손대지 않습니다.

```
di{v1}erent                                   → different     (사전에 있음)
<style id='4'>temporal-di</style>{v6}erence   → difference    (태그 건너뜀)
where {v1}is a small positive fraction        → 그대로        (진짜 α)
```

자리표시자만 글자로 바꾸고 **태그는 건드리지 않습니다.** 태그까지 함께 지우면 `<style>`이 짝을 잃는 배치가 있습니다. 무작위 조합 4,096건으로 오탐을 쟀고 0건이었습니다.

## 레이아웃 파손을 감지하고 되살린다

한국어를 넣으면 글자가 겹치거나 여백 밖으로 밀려나는 페이지가 생깁니다. **그런데 텍스트 추출로는 이게 보이지 않습니다.** 한글 비율도 정상이고 미번역도 아닙니다. 지표만 보면 멀쩡한데 실물은 못 읽습니다.

렌더링된 페이지에서 **단어의 실제 좌표를 원본과 대조**해 세 가지를 잽니다 — 겹침, 영역이탈, 줄충돌. 여기에 그림 속 라벨 일부만 번역되어 언어가 섞이는 경우를 따로 셉니다.

절대 기준으로 재면 안 됩니다. 수식이 빽빽한 페이지는 **원본에서도** 상자가 겹치게 조판되어 있습니다(위·아래 첨자, 큰 괄호). 같은 지표를 원본에서도 재고 **늘어난 만큼만** 봅니다.

렌더링된 픽셀의 잉크 농도로도 재봤지만 원리적으로 부족했습니다. 한국어로 바뀌면 글자 수가 줄어 잉크가 옅어지는 게 정상이라(중앙값 0.84배), 파손됐는데도 옅은 페이지를 구분할 수 없습니다.

```
                     텍스트 지표   잉크 농도    단어 좌표
겹쳐서 못 읽는 쪽        통과      3.38 ✓      겹침 57% ✓
여백으로 밀려난 쪽        통과      1.41 ✗      이탈 19% ✓
글자가 뒤섞인 쪽         통과      0.64 ✗      이탈 14% ✓
그림 라벨만 섞인 쪽       통과      0.69 ✗      그림혼재 ✓
```

### 되살리는 순서

감지했으면 되살려야 합니다. 원문으로 돌려놓는 것은 고치는 게 아니라 포기하는 것입니다.

```
1단계  그 페이지만 '간결하게' 다시 번역한다   ← 겹침의 원인은 길이다
2단계  그래도 안 되면 원문 페이지를 그대로 쓴다
```

1단계는 그 한 쪽만 다시 돌리므로 40쪽 구간을 재번역할 필요가 없습니다. 실측으로 겹침 99%로 표시한 페이지가 간결 재번역만으로 한국어(1,046자)를 유지한 채 정상 판정을 받았습니다.

재번역 결과가 실제로 한국어인지 확인한 뒤에 끼웁니다. 종료 코드만으로는 부족합니다 — 상류가 죽어 있어도 **BabelDOC은 0을 돌려주고 영어 페이지를 내놓습니다.**

2단계까지 간 페이지는 영어로 남습니다. 그때는 조용히 바꿔치기하지 않고 해당 쪽 하단에 표시를 남기고 보고서에 기록합니다.

## 실패한 항목만 다시 보낸다

배치 10개 중 1개가 틀렸다고 10개를 재번역하면 GPU가 재작업만 합니다. 항목별로 검증해 실패한 것만 골라 다시 보내고, 그때 **"당신은 `{v38}`을 빠뜨렸다"**고 이름으로 지목합니다.

## 캐시는 문단 단위다

번역 엔진은 실행마다 문단을 다르게 묶고 번호를 다시 매깁니다. 배치 전체를 한 키로 해시하면 묶음이 조금만 달라져도 전부 빗나갑니다 — 500쪽 작업에서 실측 적중률 **2.18%**였습니다. 같은 문장이 실행마다 다르게 번역되어 용어까지 흔들렸습니다.

문단 하나를 캐시 한 줄로 바꾸고 id를 키에서 뺐습니다.

| 시나리오 | 이전 | 지금 |
|---|---|---|
| 같은 배치 재요청 | 적중 | 2/2 |
| 배치에 1개 추가 | 전부 미스 | 2/3 |
| 같은 문장, id만 다름 | 미스 | 2/2 |
| 부분집합 | 미스 | 1/1 |

3쪽 문서로 실측한 왕복 시간은 냉캐시 59초, 온캐시 19초로 **3.1배**입니다. 고정 비용(엔진 기동·조판 해석·파손 검사)이 큰 짧은 문서라 이 정도고, 쪽수가 늘수록 비율은 더 벌어집니다.

검증 규칙을 바꾸면 캐시가 자동으로 무효화되도록 **모듈 소스 전체를 해시해 키에 넣습니다.** 예전에는 함수 세 개만 해시해서, 여덟 군데를 고쳐도 지문이 그대로였습니다. 같은 수정을 네 번 반복하게 만든 원인이었습니다.

**사용자가 바꾼 것도 키에 들어갑니다.** 용어집과 추가 프롬프트를 요청 본문에서 뽑으려 했다가 실패했습니다. BabelDOC의 LLM 경로는 **system 메시지를 아예 보내지 않습니다** — 역할 지시도 용어집 표도 전부 user 메시지 한 덩어리에 말아 넣습니다. 실측으로 운영 중 요청의 역할 구성은 전부 `('user',)`였고, system을 해시한 값은 빈 문자열의 해시로 고정이었습니다. 즉 용어집을 바꿔도 키가 그대로였습니다. 지금은 파일 내용을 직접 해시해 곁길로 전달합니다.

## 용어집은 정확성 장치가 아니다

같은 8쪽을 용어집 있이/없이 번역해 비교했습니다.

| 용어 | 용어집 있음 | 용어집 없음 |
|---|---|---|
| policy | 정책 ×29 | 정책 ×29 |
| reward | 보상 ×10 | 보상 ×10 |
| state | 상태 ×40 | 상태 ×41 |
| **return** | **이득 ×4** | **수익 ×4** |
| **value function** | **가치 함수 ×3** | 가치 함수 ×2, **값 함수 ×1** |

한글 비율은 0.865로 완전히 같았습니다. 흔한 용어는 모델이 이미 정확히 옮깁니다. 용어집이 값을 하는 곳은 **역어가 갈리는 용어**와 **표기 흔들림** 둘뿐입니다.

그래서 분야별 어휘 목록을 도구에 박아 넣는 것은 방향이 틀렸습니다. 그 책에만 맞는 도구가 됩니다. 그렇다고 사용자에게 CSV 를 채우게 하는 것도 답이 아닙니다 — 그건 원클릭이 아닙니다.

**도구가 스스로 정하고 지킵니다.** 번역 전에 이 문서의 용어를 뽑아 역어를 한 번 정하고, 그 역어를 용어집으로 만들어 본 번역에 넘깁니다.

핵심은 **어느 역어가 옳은지 도구가 판단하지 않는다**는 것입니다. 무엇을 고르든 한 번만 고르는 것이 목적입니다. 같은 8쪽을 세 가지로 번역해 표기가 갈린 용어 수를 셌습니다.

| | 표기가 갈린 용어 |
|---|---|
| 통일 안 함 | 1개 — 가치 함수 ×2 / 값 함수 ×1 |
| 손으로 만든 용어집 108개 | **2개** — 업데이트 ×14 / 갱신 ×4, 과제 ×17 / 작업 ×2 |
| 자동 통일 | **0개** |

손으로 만든 용어집이 오히려 더 나빴습니다. 지정한 역어(갱신, 과제)가 모델이 자연스럽게 내는 말(업데이트, 작업)과 싸워서 둘 다 남았습니다. 자동 통일은 **모델이 이미 쓰는 말을 고정**하므로 그런 충돌이 없습니다.

비용은 미미합니다. 1쪽 미리보기에서 51초 대 50초였습니다 — 짧은 문서에는 반복되는 용어가 적어 뽑을 것도 적기 때문입니다.

`babeldoc` 에도 자동 추출(`--auto-extract-glossary`)이 있지만, 7B 모델로 8쪽을 돌렸을 때 **0개**를 뽑았고 결과물도 용어집 없음과 완전히 동일했습니다. 그래서 직접 뽑습니다.

### 분야를 모르는 채로 전문 용어 찾기

두 단계로 나눕니다. **통계는 후보만 모으고, 무엇이 용어인지는 모델이 정합니다.**

통계 쪽은 세 신호를 씁니다(490쪽에 12초, LLM 없음).

1. **반복되는 두 낱말 구** — `value function`, `dynamic programming`
2. **하이픈 낱말** — `off-policy`, `semi-gradient`
3. **이탤릭으로 쓰인 적 있는 단일어** — 교재는 용어를 처음 정의할 때 이탤릭으로 씁니다

구와 하이픈 낱말을 단일어보다 **앞에** 둡니다. 빈도만으로 줄을 세우면 `after`, `better` 같은 흔한 낱말이 `value function` 앞에 옵니다. 구가 전문 용어일 확률이 높다는 것은 분야가 아니라 형태에 대한 사실이라 어느 문서에나 통합니다.

그다음 모델에게 묻습니다 — "이 목록에서 이 책의 전문 용어만 남겨라". 흔한 낱말을 어휘 목록으로 거르면 그 순간 분야 전용 도구가 됩니다. 실제로 한때 잡음을 줄이려고 `learning`, `method`, `system` 을 금지어에 넣었는데, 머신러닝 교재에서 `learning` 은 막아야 할 잡음이 아니라 **가장 중요한 용어**였습니다.

    넣은 것:  value function · off-policy · membrane potential · ion channel
              after · better · right · general · case · complete · single …
    남은 것:  value function · off-policy · membrane potential · ion channel
    → 잡음 9개 중 9개 제거, 진짜 용어 6개 전부 보존

이 요청은 **추론 서버에 직접** 보냅니다. 미들웨어 프록시로 보내면 번역가 지시문이 붙어 모델이 "골라라"를 "옮겨라"로 받아들입니다. 실측으로 프록시를 거치니 잡음 9개 중 0개가 걸러졌습니다.

남는 것은 원문과 **정확히 일치하는 항목만**입니다. 손상된 항목에 대해 모델은 버리는 대신 고쳐서 돌려주는 일이 있는데(`nite-horizon` → `finite horizon`), 그 교정본은 실제 문서에 없는 문자열이라 용어집에 넣어 봐야 아무 데도 걸리지 않습니다. 일치 검사만으로 손상 항목 제거가 따라옵니다 — 실측 5개 중 5개.

추출 전에 합자 복구를 먼저 돌립니다. 안 그러면 `arti cial`(artificial)과 `erent`(different)가 상위 후보로 올라옵니다.


## 같은 프로세스를 두 번 믿지 않는다

`uvicorn`은 `--reload` 없이 뜨면 **기동 시점의 코드를 계속 씁니다.** 그런데 예전 구현은 `/health`가 응답하기만 하면 그 프록시를 재사용했습니다. 그래서 소스를 고쳐도 몇 시간 묵은 프로세스가 계속 서비스했고, 검증은 전부 옛 코드를 상대로 이루어졌습니다.

이 프로젝트에서 가장 많은 시간을 잡아먹은 실패입니다. 13시간 된 프로세스를 상대로 "고쳤다"를 반복했습니다.

지금은 `/health`가 규칙 지문을 내보내고, 지문이 다르면 살아 있어도 죽은 것으로 봅니다.

다만 **갈아치우지는 않습니다.** 처음 구현은 포트를 쥔 프로세스를 그냥 죽였습니다. 우리 것인지 보지도 않고. 8100은 흔한 개발 포트라, 이 도구를 처음 받아 실행한 사람이 무관한 서버를 잃습니다. 두 번역을 동시에 돌리면 나중 것이 먼저 것의 프록시를 죽였고, 먼저 것은 합자 사전 없는 프록시로 넘어가 한국어 본문에 `↵`가 15개 박힌 채 **"파손 0쪽"이라고 보고했습니다.**

지금은 `/health`의 모양으로 우리 것인지 확인하고, 남의 것이면 죽이지 않고 **다음 빈 포트로 비켜 갑니다.** 같은 작업 디렉터리의 프록시만 이어 씁니다.

## GPU 사용률

ollama 로그의 `offloaded N/M layers`에서 N과 M이 다르면 일부가 CPU에서 돌고 있다는 뜻이고, 토큰마다 CPU를 왕복하느라 GPU가 20%대에 머뭅니다.

슬롯 수를 늘리면 KV 캐시가 커져 오히려 레이어를 GPU 밖으로 밀어냅니다. 이 도구는 8슬롯으로 고정해 12GB에서 전 레이어가 GPU에 남도록 했습니다.
